# Demon Roulette

Windows-only MSVC console C++ project: a networked 2-player "Buckshot Roulette"-style game. Three .exe (Start / Server / Client) plus one shared header `common.h`. The codebase is maintained by hand — comments in the source are in Chinese and should be kept up to date.

## Build

- `build.bat` compiles all three with `cl` — requires an MSVC Developer Command Prompt (`vcvars64.bat`); `cl` is NOT on a normal PATH.
- Per-file command (Client additionally links `user32.lib`):
  `cl /utf-8 /MT /EHsc /D "_CRT_SECURE_NO_WARNINGS" <File>.cpp /link ws2_32.lib /SUBSYSTEM:CONSOLE /OUT:<File>.exe`
- Sources are UTF-8 (no BOM); `/utf-8` is required or `cl` misreads them as GBK(936) and the build fails with a C4819/C2001 cascade. All three `main()`s call `SetConsoleUtf8()` (via `common.h`) so UTF-8 string literals render correctly on the console.
- No CMake/Makefile. Runtime order: Start.exe first, then Client.exe.

## Architecture

- **common.h** — shared utilities: `LogMsg` (timestamped append + returns string for console), `ReceiveLines` (line-buffered recv, `\r`-stripped), `SanitizeName`/`SanitizeChat` (injection guards), `IsValidPort` (1024-65535), console helpers (`SetConsoleUtf8` sets both CPs to UTF-8). `#pragma comment(lib, "ws2_32.lib")` and `_WIN32_WINNT` live here.
- **Start.exe** (Start.cpp) — room manager, listens on 8888. Rooms keyed by user-chosen port; when 2 players are READY it spawns Server.exe per room via `CreateProcessW` (wide API):
  `Server.exe <gamePort> "<name1>" "<name2>" <startIp> <startPort> <roomId>`. On game end it resets the room via `GAME_ENDED`, or destroys it via `RELEASE`. **Fixed:** Spawn now uses wide command line so CJK names pass losslessly; Server.cpp parses argv via `CommandLineToArgvW` → UTF-8.
- **Server.exe** (Server.cpp) — one game per process. 3 threads: main (game logic), accept (first connect + reconnect + `GIVEUP`), recv (both players' messages).
- **Client.exe** (Client.cpp) — lobby → room → game. 4 threads: main (dispatch; `__INPUT__` waits on `g_gameCmdQueue` and bails on `Game over`/`__CONN_LOST__`), input (**gated by `g_inputGate`**; reads console via `ReadConsoleW` via 50 ms `WaitForSingleObject` polling — routes to `g_gameCmdQueue` in-game, `g_cmdQueue` otherwise; **Open** = capture a line, **Closed** = read-and-discard (raw mode, no echo, cursor hidden), **Paused** = never read), room-recv, game-recv. **The recv threads are rebuilt on every (re)connect** — this is what makes post-game rejoin work.
- Pauses (`[ Pause ]`) are **`system("pause > nul")`** (both `PauseAndWait()` and the `__PAUSE__` handler): print `"\n[ Pause ]\n"`, switch the gate to `Paused` (input thread stops reading entirely — no more racing cmd.exe for the Enter), `FlushConsoleInputBuffer` before and after, then run `system("pause > nul")`. The console mode is set to raw (no echo/line input) in non-Open gate states via `SetInputGate()`, so stray keys during a pause are invisible and get flushed. `__INPUT__` **never drains** `g_gameCmdQueue` and **skips empty lines** before taking the first non-empty one. The command queues are `deque<string>` to allow front/back inspection.

## Room lifecycle & disconnect rules

- Client closes its RM socket when entering a game; RM keeps the room with empty slots (names preserved). After the game, both clients reconnect to RM and send `GAME_ENDED|<roomId>` then `REJOIN|<roomId>|<playerId>` to re-attach (preferred slot first, then any free slot; 1-slot becomes admin).
- Single-player disconnect: client tries 3 game reconnects (~5s apart); both clients see status text. On failure client sends `GIVEUP|N` → server aborts the game, room is **kept**, both players rejoin (admin promoted if original admin is gone).
- Both players lost: server sends `GAME_ENDED|<roomId>` + `RELEASE|<roomId>` → RM destroys the room → rejoin fails → clients land in lobby.
- RM unreachable after a game: client retries 3×, then prints `[ Pause ]` and exits.
- Server waits up to 25 s (`RECONNECT_TIMEOUT_SECONDS` in Server.cpp) for a reconnect as a crash backstop.

## Wire protocol

Newline-terminated plain text, `|`-separated fields (unified 2025-08-01; Start.cpp parsers tolerate both `|` and space for transition).

- Client→RM: `HELLO|START`, `NAME|<n>`, `LIST`, `CREATE|<port>`, `JOIN|<port>`, `READY`, `PICK` (admin), `STATUS` (in-room: query ready status), `EXIT`, `GAME_ENDED|<roomId>`, `REJOIN|<roomId>|<playerId>`. Local console commands: `HELP` (print command list, valid in all states), `cls`/`clear`, `STATUS` (in-room ready status), `NAME|<name>` (or `NAME <name>`).
- RM→Client: `WELCOME|`, `ROOMS_LIST|`, `CREATED|<id>|<port>`, `JOINED|<id>`, `ADMIN|`, `ROOM_EVENT|`, `READY_STATUS|`, `ROOM_STATUS|<name1>|<ready1>|<name2>|<ready2>`, `GAME_PREPARE|<port>|<roomId>|<ip>|<playerId>`, `GAME_ENDED|<id>`, `REJOIN_FAIL|`, `KICKED|`, `ERROR:`
- Server→RM: `GAME_ENDED|<roomId>`, `RELEASE|<roomId>` (both sent on one connection prefixed by `HELLO|START`)
- Game: client connects then sends `PLAYER_ID|1|2` (or `GIVEUP|N`). Server control messages: `__CLS__`, `__PAUSE__`, `__INPUT__`, `__PROGRESS__:<n>`, `__TYPEWRITER__<c>`. Player choices are `PLAYER_N|<text>` (prefixed with player's own id). Game ends on `Game over.`/`Game over`; socket drop triggers `__CONN_LOST__` → reconnect flow.

## Gotchas

- Player indices are 1/2 (arrays sized [3], [0] unused). All game state lives in globals; one game per process.
- `wait(f)` is a pacing helper backed by `Sleep` (no busy-wait). `-100` = pause; `f<0` 400 ms/unit; `f==0` 50 ms; `0<f<100` 100 ms/unit; `f>=100` 5 ms/unit.
- Thread-safe sends require `SendToAll`/`SendToClient`; never touch `g_connected`/`g_clients` directly without `g_mutex`. **Sends are lock-free**: sockets are snapshotted under the lock, `send` runs outside it (a blocked TCP send no longer stalls the recv/accept threads); failures go back through `MarkDisconnected(id, sock)` with socket-identity checks. Avoid nested `send` while holding locks.
- `Ask()` accepts debug commands `-1` (swap in a real shell) and `-2` (swap in a blank) — left in deliberately, don't remove.
- During a player's choice (Ask / Chocolate target pick), menu redraws, `-1`/`-2` refresh, errors and `__PAUSE__` are sent **only to the choosing client** (`SendToClient(currentId, ...)`, including `__CLS__`); only the final result is broadcast (`SendToAll`). The opponent's screen just shows "X is choosing ..." — no repaints, no menu leak (2026-08-03).
- Logs append to `server.log` / `client.log` / `start.log` in cwd; `clear.bat` truncates, `copy.bat` exports all to clipboard.
- `data.txt` appends winner + bonus per finished game.
- `gameServerIp` is hardcoded `127.0.0.1` — local play only.
- RM `LIST` shows in-game rooms as `<port>\t2/2 [in-game]` (not joinable — players are in the game server); hides countdown/port-reserved rooms and rooms whose both slots are empty (returning players use `REJOIN`). The 2/2 is **fixed** — once a game starts both clients close their lobby sockets, so counting by socket would print 1/2 and mislead players. `JOIN` rejects rooms with `gameEnded` or `gameStarted`; `CREATE` rejects **any** port already held by an existing room (in-game included) so two rooms can never share a game port.
- Server `AcceptThreadFunc` first-line read uses a 30 s `select` timeout (connect-and-go-silent clients are dropped); `WaitForPlayerInput` handles the *other* player's `__DISCONNECT__` by entering `WaitForReconnect` (game aborts if they give up/time out) instead of ignoring it.
- Start.cpp `SendToClient` closes the socket on send failure, and accepted sockets get a 5 s `SO_SNDTIMEO` — a client that stops reading can stall a lock-held `send` for at most 5 s, then its `HandleClient` recv loop notices the closed socket and runs cleanup.
- **Input thread is gate-driven, not always-reading.** `SetInputGate()` (main thread only) toggles `g_inputGate` (`Open`/`Closed`/`Paused`) and the console input mode (raw without echo/line input unless `Open`). `Open` (lobby/room prompt, game `__INPUT__`) → input thread captures one line; `Closed` (game output/typewriter/progress) → it reads and discards via `ReadConsoleInput` (never `ReadConsoleW`, which blocks on non-char events like focus changes) so stale keys can't leak into the next `__INPUT__`; `Paused` → it never touches the console (lets `system("pause")` own the Enter). Cursor visibility is driven by the same transitions (`ShowCursor`). The previous always-reading design let keys typed during game output leak into the game queues (stale-input bugs); a naive `g_acceptInput` gate (2025-08-01) broke lobby input — the current design instead changes *what the thread does* (read-and-discard vs read-and-route) rather than stopping it.
- **Pause is `system("pause > nul")` in Client.cpp** (`PauseAndWait` + `__PAUSE__` handler): switch gate to `Paused`, flush the input buffer before and after (so leftover keys don't skip the pause and keys typed during it don't leak), then `system("pause > nul")`. Safe because the input thread is guaranteed not to read while it runs. The old CV-driven path (`g_pausePending`/`g_pauseCV` and queue-consuming pauses) is gone. `system("pause > nul")` in `Start.cpp`/`Server.cpp` `main` is the process-shutdown path (no input thread).
- Server waits up to 25 s (`RECONNECT_TIMEOUT_SECONDS` in Server.cpp) for a reconnect as a crash backstop; `WaitForGameStart()` uses the same timeout so a player who never connects can't hang the process forever (the game then aborts and notifies the RM). 25 s comfortably covers the client's own 3× ~5 s reconnect window; 60 s previously left the surviving client stuck "waiting for reconnect" ~a minute, which the user reported as an infinite hang.
- Start.cpp's `HandleClient` first-line handshake (`HELLO|START`) is read with a 30 s `select` timeout + partial-packet reassembly; a connect-and-go-silent client can no longer occupy a thread forever. The server's `AcceptThreadFunc` reads only the first line manually (with the same 30 s select timeout) and hands any same-packet trailing bytes back to the recv thread's buffer, so the player's first game message is never swallowed.

## Known bugs (fix status per 2025-08-01; 2026-08-03 batch)

- **data.txt always records 0 bonus.** `Server.cpp _Bonus()` divided the global `Bonus` to 0 while building the typewriter string; `Save()` wrote the now-zero value. **Fixed 2026-08-03:** `_Bonus()` works on a local copy; real bonus is saved. Verified: post-fix runs append e.g. `Tester2 8278000000`.
- **Duplicate rooms on one port / in-game room invisible in LIST.** Old `CREATE` only rejected ports of `!gameStarted` rooms, so a room whose game was running (or game-ended) could be re-created on the same port → two `Server.exe` fighting over one port (bind 10048; players landed on the wrong server). Old `LIST` hid in-game rooms entirely, so a third client saw an "empty" list. **Fixed 2026-08-03:** `CREATE` rejects any existing port; `LIST` shows in-game rooms as `<port>\t2/2 [in-game]`. The 2/2 is fixed (not a socket count): both clients close their lobby sockets on `GAME_PREPARE`, so counting sockets printed 1/2. Verified by harness client C: `ROOMS_LIST:5000 2/2 [in-game]` + `ERROR:Port already in use`.
- **LIST showed in-game rooms as 1/2 instead of 2/2.** The slot count was derived from `room.client2 != INVALID_SOCKET`, but both players close their lobby connections at game start, so the room always looked half-empty. **Fixed 2026-08-03:** in-game rooms print a fixed `2/2`.
- **Surviving player sat idling while the opponent never reconnected.** `WaitForReconnect` waited up to 60 s, which the user perceived as an infinite hang when one client quit mid-game. **Fixed 2026-08-03:** `RECONNECT_TIMEOUT_SECONDS` is 25 s (covers the client's own 3× reconnect attempts); on give-up/timeout the abandoned player is returned to the room (room kept, `GAME_ENDED` only — no `RELEASE`).
- **WaitForPlayerInput ignored the other player's disconnect.** Only the current player's `__DISCONNECT__` triggered a reconnect wait; the opponent's went unhandled, so both sides could sit indefinitely. **Fixed 2026-08-03:** opponent disconnect now enters `WaitForReconnect(opponent)`; give-up/timeout ends the game.
- **AcceptThreadFunc first-line recv had no timeout.** A client that connected and never sent data blocked the accept thread forever (it also serves the other player's reconnects). **Fixed 2026-08-03:** 30 s `select` guard before the first-line `recv`.
- **Lock-held blocking sends in Start.cpp.** `SendToClient` can be called while `g_roomsMutex`/`g_clientsMutex` is held (READY/PICK/REJOIN/STATUS...); a client that stops reading (full TCP window) would block the whole room manager forever. **Fixed 2026-08-03:** 5 s `SO_SNDTIMEO` on accepted sockets + close-on-send-failure in `SendToClient` (HandleClient's recv loop then runs cleanup).
- **GAME_PREPARE sent before the game server was listening.** Old order: notify clients → sleep 500 ms → spawn. Clients connected to a not-yet-listening port and bounced back to the room. **Fixed 2026-08-03:** spawn `Server.exe` first, send `GAME_PREPARE` only on success; Client.cpp retries the connect 5× (1 s apart, socket recreated per attempt).
- **ShowHP comment vs code contradiction.** Comment claimed round 3 HP cap is 3; code caps round 3 at 5 (`'-'` is only the bar glyph). **Fixed 2026-08-03:** comment now matches code; the round-3 `Hp<=2` smoke ban is documented as an intentional final-round rule.
- **CJK names corrupted across StartServer spawn.** `Start.cpp` builds cmdLine from UTF-8 `name1`/`name2`, but `CreateProcess A` was ANSI. On a GBK (936) console the UTF-8 bytes were reinterpreted. **Fixed:** `CreateProcessW` with wide cmdLine (UTF-8→wide via `MultiByteToWideChar`); Server `main` uses `GetCommandLineW`+`CommandLineToArgvW`→UTF-8 via `WideCharToMultiByte(CP_UTF8)`.
- **CJK name mojibake at truncation.** `SanitizeName` (common.h) truncates to 20 bytes and then **validates the tail UTF-8 sequence**: it walks back from the end counting continuation bytes (0x80–0xBF), computes how many the leading byte requires, and erases only incomplete sequences. The old version unconditionally stripped all trailing continuation bytes, which corrupted the last char (complete CJK chars end in a continuation byte, e.g. 张 = E5 BC A0). **Fixed 2025-08-01.**
- **Pause key-mashing.** `system("pause > nul")` spawned a cmd.exe that raced the input thread's `ReadConsoleW` for console input; the Enter that dismissed the pause was often consumed by the input thread first (becoming a stray empty line), so several presses were needed. **Fixed 2025-08-01 with a CV-driven wait** (consume only the trailing empty line; fall back to `system("pause > nul")` when the input thread hasn't started). **Reworked 2026-08-02:** the CV path is replaced by `system("pause > nul")` again — safe now because the input gate's `Paused` state guarantees the input thread never reads the console while cmd.exe's pause owns it, and the console buffer is flushed before/after so the pause can't be skipped or leak keys.
- **Input no-response / misalignment.** **Fixed 2025-08-01:** (1) `__INPUT__` drained `g_gameCmdQueue`, discarding the answer the player typed between the server's prompt text and the `__INPUT__` message (they arrive back-to-back, so the answer is usually already queued) — the drain is removed; (2) `__PAUSE__` popped the queue front, eating a pre-typed choice as if it were the pause Enter — pauses now consume only the trailing empty line, preserving the choice for the next `__INPUT__`; (3) `__INPUT__` skips leftover empty lines and takes the first non-empty one. **2026-08-02:** the input gate (`Open` only during `__INPUT__`/prompt, `Closed` elsewhere with read-and-discard) makes stale keys impossible by construction — anything typed outside an input window is drained and dropped before the gate reopens. **2026-08-02 (final design):** game input now uses a **solicited window** instead of a blocking read — the client's `__INPUT__` handler just sets `g_inputSolicited`, shows the cursor and opens the gate, then returns so the message loop keeps running; the input thread routes captured lines to `g_gameCmdQueue` **only while solicited** (otherwise it discards them, keeping the stale-key protection); each main-loop iteration calls `FlushGameInput()` which skips empty lines, sends the first non-empty one as `PLAYER_N|<line>`, clears the rest of the queue and closes the window. A blocking `__INPUT__` handler was a regression (menu appeared only after typing) — never block the message loop on input. `g_inputSolicited` is reset on `__CONN_LOST__`, `ReturnToRoom()` and `GAME_PREPARE`. **2026-08-03:** the server sends `__INPUT__` *after* the menu/prompt text (in `Ask()`, `Shoot()`, `Chocolate()`) so the gate only opens exactly at the prompt — menu printing runs with the gate Closed (no echo, keys read-and-discarded), so type-ahead/smash during printing can't corrupt the menu layout or the cursor position anymore (previously `__INPUT__` was sent first for type-ahead convenience, which let early keystrokes interleave with the printed menu).
- **Room destroyed when the game starts.** Client closes its RM socket immediately on `GAME_PREPARE` (Client.cpp), but `StartGameServer` used to set `room.gameStarted = true` only 1.5 s later — both disconnects landed inside that window, `RemovePlayerFromRoom` saw `gameStarting && !gameStarted`, cancelled the "countdown" and destroyed the now-empty room, so after the game `REJOIN` failed with "Room no longer exists" and both players dropped to the lobby. **Fixed 2026-08-02:** `StartGameServer` marks `gameStarted = true` (and `gameStarting = false`) inside the lock *before* sending `GAME_PREPARE`; the late 1.5 s re-set is gone. On spawn failure the flags are still reverted so returning players can `REJOIN`.
- **STATUS command mismatch.** `STATUS` was documented as "refresh room ready status" but was an alias for `LIST` (printed the global room list). **Fixed 2026-08-02:** the client sends `STATUS` to the RM; the RM replies `ROOM_STATUS|<name1>|<ready1>|<name2>|<ready2>` for the player's own room (in-room only), which the client formats into a readable status block.
- **Post-game prompt missing / stray lobby commands.** **Fixed 2025-08-01:** `ReturnToRoom()` resets `g_promptDisplayed` (lobby prompt re-appears after a game), flushes the console input buffer (`FlushConsoleInputBuffer`, not an Enter injection — injection completed half-typed in-game lines and misrouted them as lobby commands) and clears both command queues. `GAME_PREPARE` clears `g_cmdQueue` too (commands typed while connecting used to fire after returning to the room) and resets `g_promptDisplayed` so game text can't append to the lobby prompt.
- **Lobby prompt disappeared after any command — a spare Enter was needed to bring it back.** Delivering a command never reset `g_promptDisplayed`, so the trailing `ShowPrompt()` at the bottom of the main loop was a no-op; only an empty-line (bare Enter) command forced a redraw. **Fixed 2026-08-03:** the command-consumption path resets `g_promptDisplayed` when a line is popped from `g_cmdQueue`, and the loop now distinguishes commands that wait on a server reply (`cmdAwaitReply = true` for LIST/CREATE/JOIN/NAME/READY/PICK/STATUS/in-room chat — the reply's `msgHandled` path redraws) from locally-handled/unknown ones (redrawn immediately at the loop bottom). Every input now returns to the prompt like a CLI; no extra Enter.
- **Wire protocol separator inconsistency.** Space used for `GAME_ENDED`, `RELEASE`, `NAME` at top-level; `:` for client choices. **Fixed:** unified all to `|` (Client/RM/Server). Start parsers tolerate both `|` and space for transition. Client choice msg `PLAYER_<text>` → `PLAYER|text>`.
- **Always-readable input thread.** `InputThreadFunc` (Client.cpp) reads unconditionally via polling. Keys typed while cursor hidden (game output/typewriter) get buffered into `g_cmdQueue`/`g_gameCmdQueue` and consumed later. **Fixed 2026-08-02 by the input gate**: see the Gotchas entry above — `Open` reads-and-routes, `Closed` reads-and-discards (raw mode, no echo, cursor hidden), `Paused` reads nothing. The previous `g_acceptInput` gate failure (lobby prompt skip) came from *stopping* the thread; the current design keeps the thread running and only changes what it does with the input. Startup IP/port input is now validated (IPv4 format, port 1024-65535) with re-prompts instead of failing after 3 connect retries.
- **Startup keystroke bleed.** Startup reads name/IP/port via `ReadConsoleUtf8Line` on main thread before `g_inputThread` starts. Tail keystrokes after final Enter can bleed into the first `ReadConsoleW` of the input thread. **Fixed 2026-08-02:** the console buffer is flushed right before the input thread starts; the gate is `Closed` until then, and `SetInputGate(Open)` is applied together with the lobby prompt.
